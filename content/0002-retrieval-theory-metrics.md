## Core idea

### 〇、检索基础:数据结构的演进(哈希 / 树 / 跳表)

在讲倒排索引之前,先建立检索数据结构的坐标系。检索技术经典教材前三讲把检索的基本形态讲透了:

| 结构 | 查询效率 | 适用场景 | 典型代表 |
|---|---|---|---|
| 有序数组 | O(log n) 二分 | 静态数据,读多写少 | 基础索引 |
| 二叉检索树 | O(log n) | 动态数据,增删频繁 | BST/AVL/红黑树 |
| 跳表 | O(log n) | 内存中的有序结构 | Redis ZSET |
| 哈希表 | O(1) | 精确 key 查询 | 用户 ID → 用户信息 |
| 位图 | O(1) 存在性 | 判断元素是否存在 | 布隆过滤器 |

**哈希检索(03 讲)**:给定用户 ID 查用户信息,数组下标 = ID,直接 O(1)。但哈希有碰撞、有扩容,工业实现远没这么简单。**核心思想:用空间换时间,把 key 直接映射到位置**。

**状态检索(04 讲)**:判断"用户 ID 是否存在"这类问题,不需要存完整数据,只需要存在性。位图一个 bit 一个状态,1 亿个用户只要 12.5MB。**核心思想:问题只需要"是/否"时,别存多余信息**。

**B+树(06 讲)**:海量磁盘数据,数据不能全放内存。B+树叶子节点存数据、内部节点只存索引,一个节点 = 一个磁盘页,层高只有 3-4 层,随机读变顺序读。MySQL/PostgreSQL 的默认索引。**核心思想:用"宽树"把磁盘 IO 次数压到常数**。

**LSM 树(07 讲)**:日志系统每秒上万条写入,B+树每次插入都随机写磁盘,慢。LSM 先写内存(有序表),攒够批量落盘(顺序写),再后台合并。写入快、读稍慢。LevelDB/RocksDB/Cassandra 都用它。**核心思想:把随机写变成顺序写,用合并换写性能**。

**和 RAG 的关系**:向量库(pgvector/HNSW)解决的是"相似度检索",但元数据过滤、精确匹配、权限判断这些还是靠传统结构。比如 WeKnora 里 `SearchTarget` 的 `TagIDs` 过滤,底层就是精确索引;布隆过滤器/位图在去重(wiki_ingest_dedup)里就有应用。**RAG 不是只靠向量,精确检索结构是混合检索的关键词路底座**。

### 一、倒排索引:为什么数据库做不了全文搜索

一个最直观的对比来自 ES 商品搜索实战:数据库 LIKE 搜索 = 全表扫描 + 逐字比对,O(n·k) 慢到没法用;ES 的答案是**倒排索引**——以"单词"为 key,value 是包含该词的所有文档 ID 列表。

```text
正排索引(数据库/文档视角):doc1 → {苹果, 手机, 新品}
                            doc2 → {苹果, 红富士, 水果}

倒排索引(单词视角):       苹果 → [doc1, doc2]
                            手机 → [doc1]
                            红富士 → [doc2]
```

查询"苹果手机" = 对"苹果""手机"两个词各查一次倒排表,两次树查找,复杂度相当于二次命中索引,比全表扫描快几个数量级。**倒排表物理存储和 InnoDB 索引一样是查找树,不是二维表**。这就是 RAG 关键词检索(BM25/ParadeDB)的理论底座。

WeKnora 落点:混合检索的 Keywords 路(`internal/application/repository/retriever/` 的 ParadeDB repo)底层就是倒排索引,`content ||| ?` 语法触发的正是这个词表查找。

### 一·五、索引的工程:构建 / 更新 / 拆分(08-10 讲)

有了倒排索引的结构,搜索引擎怎么在海量数据上真正建起来、保持新鲜、扛住规模?检索技术经典教材 08-10 讲给了三个工程答案,WeKnora 的索引管线也遵循同一套思想:

**① 构建(08 讲):大于内存的倒排索引怎么生成?**

小文档集可以在内存建哈希倒排表,万亿网页显然不行。工业做法是**多路归并**:

```text
1. 把文档分批读入内存,每批建一个内存倒排表
2. 内存倒排表写盘(有序),一批一个文件
3. 多个有序文件多路归并,合成一个大倒排索引
```

**核心思想:任何"内存放不下"的大数据,都可以用"分片 + 归并"解决**。这和外部排序、MapReduce 是同一个思想。

**② 更新(09 讲):刚发布的文章为什么马上能被搜到?**

全量重建索引太贵,增量更新又怕丢失。工业标准做法是**两层索引**:

```text
内存索引(实时):新文档先进内存,立刻可搜
磁盘索引(全量):定期把内存索引合并进磁盘大索引
```

查询时两层都查、结果合并去重。新文档秒级可见,老索引不用天天重建。

**③ 拆分(10 讲):大规模检索系统怎么用分布式加速?**

倒排索引按**文档分片**(每台机器存一部分文档的索引)或**词项分片**(每台机器管一部分词的倒排表)。查询路由到相关分片,并行检索再合并。**核心思想:索引也是数据,可以水平切分**。

**WeKnora 落点**:虽然 WeKnora 用的是现成检索后端(pgvector/ParadeDB),但理解这套"分片 + 归并 + 两层索引"让你能看懂:
- 为什么 `pgvector` 建 HNSW 索引要 `CREATE INDEX... ON embeddings USING hnsw` 且建大索引很慢(它是离线的,查询走 ANN,更新是增量的)
- 为什么混合检索要"非精准召回 + 精准排序"两阶段(08/12 讲的成本权衡)
- 面试被问"千万级文档 RAG 怎么设计"时,这套工程思想就是答案骨架

### 二、打分:从 TF-IDF 到 BM25

有了倒排表,怎么给结果排序?经典答案是 **TF-IDF**:

- **TF(词频)**:词在文档里出现越多越重要
- **DF(文档频率)**:词出现在越多的文档里越普遍、越没区分度("的"字几乎每篇都有)
- **IDF(逆文档频率)**:DF 的倒数,词越稀有越有区分度
- **相关性 ≈ TF × IDF**(对数平滑)

BM25 是 TF-IDF 的现代升级,加了三个修正:**文档长度归一化**(长文档词频要打折)、**词频饱和**(词频再高贡献也封顶)、**可调参数**(k1、b 控制饱和与长度惩罚)。BM25 是今天 ES/ParadeDB 的事实标准,也是 WeKnora 关键词检索用的。

```text
BM25 直觉:匹配"红富士"的文档,比匹配"苹果"的文档更稀有、更该排前面
(因为"苹果"在 1 万篇文档里出现,"红富士"只在 3 篇出现)
```

WeKnora 落点:`content ||| ?` 返回的 `paradedb.score(id)` 就是 BM25 分数,混合检索里跟 pgvector 的余弦距离(`<=>`)双路取分。

### 三、TopK:精准 vs 非精准(工业界两阶段)

关键洞察:**精准 TopK 打分太贵,工业界用"非精准 TopK + 精准 TopK"两阶段**:

1. **非精准 TopK**:先快速粗筛(用简化打分/跳表/位图/倒排加速),把"足够好的结果"装进候选集——不求排序精准,只求高质量结果没被漏掉
2. **精准 TopK**:对候选集(通常几百条)做完整打分排序,输出最终 Top K

为什么可以接受非精准?因为用户没有明确目标,第一页只要"质量够高就行",不必是全局最高分。**这是检索系统性能与质量的核心权衡**。

WeKnora 落点:混合检索双路召回(每路取候选)→ `fuseWithRRF` 融合 → rerank 重排(精确打分)→ 取 TopK。整套就是"非精准召回 + 精准排序"的工程化。

### 四、最近邻检索:向量搜索的理论(LSH / PQ / HNSW)

向量检索解决的是"相似度检索":给定查询向量,找到库里最相似的 K 个。暴力的全量比较 O(n·d) 在大规模下不可行,工业界有三级方案(15/16 讲 + 现代实现):

**① 局部敏感哈希(LSH,15 讲)**

核心思想:**让相似向量以高概率落入同一个桶**。对向量做多次随机投影,每次投影得到一组"桶号"——相似的向量在多数投影下会分到同桶。查询时只搜查询向量所在桶,再做精确比较。

```text
两个相似的文档向量 → 多数随机投影后落同桶 → 只比较同桶内文档
核心:把"高维相似度比较"降维成"桶号比较",先粗筛再精排
```

代价:召回率有损失(相似的可能被分到不同桶),用多张哈希表(多个投影组)降低漏检率。检索技术核心20讲的 LSH 课还给了两种更实用的形态:**SimHash**(用一次普通哈希 + 权重叠加,给每个文档生成一个 64 位指纹)和**相似检索加速**(用海明距离衡量指纹相近程度,再按"抽屉原理"分段、以段值为 key 建倒排索引,而不是逐个文档比对)。

**② 乘积量化(PQ,16 讲)**

核心思想:**把高维向量切成子空间分别量化,压缩存储**。一个 128 维向量切成 8 段,每段 16 维,每段用聚类中心(k=256)量化成 1 字节,整个向量变成 8 字节的编码(512 字节 → 8 字节,存储压缩到约 1/64),距离计算靠查近似表完成。检索技术核心20讲的乘积量化课用的例子是 1024 维分 4 段、每段聚成 256 个中心,量化后仅 32 比特,压缩到原来的 1/1024。

```text
128维 float 向量(512字节) → 切成 8 段 × 16 维 → 每段量化成 1 字节
→ 8 字节编码(512B → 8B,约 1/64),距离用近似查表
```

代价:量化有精度损失,适合"先粗筛召回,再精排"的两阶段。

**③ HNSW(现代事实标准)**

WeKnora 用的 pgvector HNSW(Hierarchical Navigable Small World)是更新的 ANN 索引:多层图结构,高层稀疏跳得快、低层密集找得准。`hnsw.ef_search` 控制搜索宽度——调大更准但更慢,调小更快但可能漏。**它是"精准排序前先非精准粗筛"思想的图索引实现,是目前向量库的主流**(pgvector/Qdrant/Milvus/Weaviate 都支持)。

**面试怎么讲**:从 LSH(桶粗筛)→ PQ(压缩近似)→ HNSW(多层图)讲 ANN 演进,再落到"为什么混合检索里向量路只要近似召回、精排交给重排"——非精准召回 + 精准排序是贯穿整个检索系统的思想。

### 五、评估指标:Precision / Recall / NDCG / MRR / MAP

WeKnora 的评估体系(`internal/application/service/metric/`)包含两族:检索指标 + 生成指标。

**检索侧(看召回质量)**:

| 指标 | 回答什么问题 | 公式直觉 | WeKnora 实现 |
|---|---|---|---|
| Precision@K | 返回的前 K 条里,多少是相关的? | 相关数 / K | metric/precision.go |
| Recall@K | 所有相关文档里,召回了几成? | 召回相关数 / 总相关数 | metric/recall.go |
| MRR | 第一个正确答案排多前? | 1 / 第一个正确结果的排名,取平均 | metric/mrr.go |
| MAP | 每个相关文档位置的精度取平均 | 平均精确率,看重整体排序质量 | metric/map.go |
| NDCG@K | 排序质量好不好(位置越靠前权重越大) | DCG / IDCG | metric/ndcg.go |

**NDCG 拆解**(metric/ndcg.go 的实现):

```text
DCG = Σ (2^rel - 1) / log2(i+2)     # i 是位置,rel 是相关性(0/1),位置越靠前折扣越小
IDCG = 理想排序下的 DCG(所有相关文档排最前)
NDCG = DCG / IDCG                     # 0~1,1 表示排序完美
```

代码里 `math.Pow(2, rel) - 1` 是增益,`math.Log2(i+2)` 是位置折扣——**排第 1 的文档权重比排第 5 的高**。WeKnora 同时算 NDCG@3 和 NDCG@10(`metric_hook.go` 注册了两份)。

**生成侧(看答案质量)**:BLEU(n-gram 重合)、ROUGE(召回式摘要评价)——见 metric/bleu.go、metric/rouge.go。

### 六、MMR:去重又保相关

重排之后还有一个问题:**检索结果可能高度重复**(同一篇文章的多个 chunk)。MMR(Maximal Marginal Relevance)在"相关"和"多样"之间做平衡:

```text
MMR = λ × relevance − (1−λ) × redundancy

relevance = 当前候选的相关分
redundancy = 当前候选与已选集合的最大相似度(WeKnora 用 Jaccard 词重叠)
λ = 0.7(WeKnora 默认,更重视相关)
```

WeKnora 的 `applyMMR`(rerank.go:457)实现要点:
- 贪心逐轮选:每轮在所有未选候选中找 MMR 最大的
- **并发预计算 token 集**:`ParallelMap` 先把所有候选分词算好(CPU 密集),避免重复分词
- 冗余度用 `searchutil.Jaccard(allTokenSets[i], selTokens)`——词集合的 Jaccard 相似度
- 选满 k 个或候选耗尽为止

```go
// rerank.go:503 核心公式
mmr:= lambda*relevance - (1.0-lambda)*redundancy
```

## Worked example

**场景**:用户搜"iPhone 激活码"。混合检索召回 8 条候选:4 条是同一篇激活码教程的不同 chunk(高度重复),2 条是别的教程,2 条是无关的。

- **不做 MMR**:重排后前 3 条全是同一篇教程的 chunk,用户看到三条几乎一样的答案
- **做 MMR(λ=0.7)**:第一条选最相关的;第二条虽然相关但和第一条 Jaccard 重叠高,MMR 被冗余度拉低,换成另一篇教程;第三条继续换。最终 3 条覆盖 3 篇不同内容,信息量最大化

**评估场景**:客服知识库改版后,拿 100 个标准问题测检索。NDCG@10 从 0.72 升到 0.85——说明"正确答案在结果列表里的位置更靠前了",虽然 Precision 没大变,但排序质量明显提升。这就是为什么 NDCG 是排序类指标、Precision 是集合类指标,要看场景选。
